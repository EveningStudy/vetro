# Vetro: instructions for coding agents

Vetro is a lightweight, clean, unified entry point for coding agents that are already installed on the user's machine: Claude Code, Codex, Antigravity and Devin. It starts the official, unmodified agent binaries, shows their sessions in one interface modelled on T3 Code, and stays out of the way. It is a thin client. It is never an agent harness.

Read `docs/ARCHITECTURE.md` before changing the core, and `docs/API.md` before touching the UI protocol.

## Product rules (never break these)

1. **Zero injection.** What the user typed is what the agent receives. Never add system prompts, developer instructions, skills, MCP servers, tools, wrapper text or replayed history. Model, mode and thinking-level choices are passed only through the agent's own switches, and only when the user changed them.
2. **Zero footprint.** Vetro writes only under `~/.vetro` (`VETRO_HOME` overrides it). Never create, modify or delete anything under `~/.claude`, `~/.codex`, `~/.gemini`, `~/.agents`, Devin's config directories, or a project workspace on Vetro's own behalf. Open other tools' SQLite files read-only and never checkpoint their WAL. (The agents themselves keep writing their own sessions and logs; that is native behaviour.)
3. **Native runtimes only.** Launch the binaries found on the machine. Never download an agent binary. Never read, copy, forward or store credentials. Sign-in always happens inside the agent's own flow.
4. **No orphans.** Every child process dies when Vetro exits (Windows Job Object; Unix process group).
5. **Light.** One Rust process. No Node, Electron or bundled browser at runtime. Idle agent processes are released and resumed on demand.
6. **Same rules for every agent.** No agent gets special restrictions or special features in the UI.
7. **Progressive disclosure.** The primary interface surfaces only user intent, items needing human action, and final answers. Intermediate reasoning, tool logs, code diffs, linked child sessions, internal or automated sessions, and raw protocol traffic stay collapsed or inside on-demand drawers by default — nothing is hidden from inspection, and nothing competes with the conversation.

## Layout

- `crates/vetro-proto`: wire contract (Rust types, TypeScript bindings generated by `cargo test -p vetro-proto`). Owned by the orchestrator: do not change it without saying so in your report.
- `crates/vetro-core`: agent adapters, session manager, history readers, linking, index, HTTP/WebSocket server.
- `crates/vetro-cli`: the `vetro` binary (`vetro serve`, `vetro probe`, ...).
- `apps/web`: React UI (Vite, Tailwind 4, Base UI). Built output is embedded in the core.
- `apps/desktop`: Tauri 2 shell.
- `docs/`: architecture, API, protocol notes per agent.

## Commands

- Rust: `cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
- Web: `pnpm --dir apps/web install`, `pnpm --dir apps/web typecheck`, `pnpm --dir apps/web build`, `pnpm --dir apps/web dev`.
- On this Windows machine cargo lives in `~/.cargo/bin`; add it to `PATH` if the shell does not have it.

## Conventions

- English in code, comments, docs and commit messages. Chinese only in `README.zh-CN.md` and UI translations.
- No comments unless the code cannot show why.
- Handle errors at real boundaries; do not wrap every line.
- New dependencies: add with `cargo add` / `pnpm add`, prefer versions published more than 7 days ago, keep the tree small. The core must stay light.
- Commits: small, imperative subject line, no AI attribution. Never push, never create remotes.
- Tests that need a live agent are `#[ignore]` and are run on purpose, never in the default test run. Default tests use the fake agents in `crates/vetro-core/tests/fixtures`.

## Live agents on the development machine

- Binaries are found the way the app finds them (`vetro agents` shows the paths). Override with `VETRO_ACP_DEVIN` and the settings file when a test needs a specific binary.
- Live tests spend the owner's quota. Keep prompts tiny (for example: reply with one word), use the cheapest model, and do not loop.
- Subscriptions have small quotas: at most a handful of short live prompts per task.
- **Antigravity: do not send prompts to `agy` (neither `agy -p` nor ACP `session/prompt`).** Handshake-level calls (`initialize`, `session/new`, `session/list`, `session/load`, `session/close`) are fine. The orchestrator runs the live Antigravity prompts itself.
- `devin acp` must be started with `--process-model in-process` in tests so no daemon is left behind. It needs the ACP `authenticate` call (`devin-browser`) in every new process; that opens a browser tab and completes by itself.
- Never run agents with permission-bypass flags against anything but a scratch directory under `.orchestra/`.

## When you are called non-interactively by the orchestrator

- Do not read, update, commit or push `~/ai-memory`; the orchestrator keeps the records.
- Do not call other agent CLIs as helpers. Starting them to test Vetro's adapters is the job; delegating your work to them is not.
- Stay inside the task. If it cannot be done as written, stop and say what is missing.
- Finish with a short report: what changed, what you ran and its result, what you could not verify, open questions.
